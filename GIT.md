# Git and GitHub delivery

Read SYSTEM.md first if it is not already loaded. For read-only Git/GitHub inspection, confirm the exact repository and item as applicable. Use the local inventory below for repository edits and local Git writes. For GitHub writes, use the remote target checks below.

## Default Git and GitHub delivery workflow

- For development delivery, confirm the repository and task, read contribution rules and related issues or pull requests, use a task branch, implement and verify, review the diff, commit, push, and create or update a pull request. Check CI and handle review feedback, then finish according to the merge conditions below. Carry out already authorized operations without asking for separate approval to commit or open a PR.
- Follow the requested scope. Analysis, review, and planning remain read-only. A request limited to issue management does not also authorize unrelated code development. The user's explicit limits such as “local changes only,” “do not commit,” or “create a PR but do not merge” take precedence. Personal configuration edits outside a repository do not require creating a repository, issue, or pull request.
- Maintain related work autonomously: reuse the current task's issue or PR, update its description, and respond to relevant review questions based on actual progress. Create an issue only when tracking has value and no duplicate exists. When managing several items, check each target and result. Do not post meaningless progress comments or promise work on behalf of others.
- Development delivery includes merging by default under the conditions below. A request only to monitor an existing PR does not authorize merging it. Follow explicit delivery limits such as PR-only or no merge. Do not impersonate a maintainer or describe your own check as another person's approval.
- Ask only for exceptional blockers. First use existing configuration and read-only investigation to identify the target. Ask a focused question only when the target remains materially ambiguous, a conflict depends on another person's intent that cannot be determined, or required authentication or runtime conditions cannot be restored independently. Explain the concrete issue and continue independent work. Already-authorized GitHub, Linear, or Notion operations are not a reason to ask.
- Preserve the working state. Local operations such as reset --hard or clean that discard existing user changes still require explicit authorization. GitHub branch deletion, force pushes, direct pushes, settings, and permission changes are authorized within the task; before using them, inspect the full diff, references, and affected collaborators. Prefer preserving history and avoid losing unrelated commits or data. Do not hide failures by disabling checks or lowering acceptance criteria.

## Standard Git workflow

1. **Confirm the state.** Before repository edits or local Git writes, confirm the repository root, branch and HEAD, worktree, unstaged and staged changes, upstream, and remote as applicable. Before GitHub writes, confirm the account, owner/repo, and exact target, including the default branch and fork/upstream relationship when they affect the operation. Verify this from GitHub when the task needs only a remote write. Confirm the publishing target independently of the directory or remote name.
2. **Isolate the task.** Record existing changes and reuse the correct task branch if one exists. Otherwise create a task branch and use a separate worktree when isolation is needed. Do not switch a worktree containing user changes, or automatically stash, move, clean, or commit someone else's work. If unexpected concurrent changes appear, recheck them; stop related writes if ownership cannot be determined.
3. **Implement and verify.** Change only the requested scope and run applicable project checks. Follow CODING.md for code and runnable behavior. Before committing, inspect the complete diff and all new files, run diff --check, and exclude credentials, unrelated changes, and generated output the project does not require tracking. State why any required check was not run.
4. **Commit precisely.** For development tasks, commit as part of the workflow. Stage explicit paths or hunks. Never use git add ., git add -A, or commit -a. Do not include or unstage content the user had already staged. If changes cannot be safely isolated, explain the blocker. Review the staged diff again before committing. Follow repository commit style and describe one logical purpose. Prefer a new fix commit over automatically amending a published commit. Do not skip hooks or change Git identity configuration.
5. **Verify the push set.** For development tasks, push the task branch as part of the workflow. Fetch and inspect the target remote, branch, complete commit set, and diff to ensure unrelated local commits are not included. Specify the remote and destination branch. Do not use --all, --mirror, or bulk tag pushes. Recheck HEAD and the worktree before pushing to catch concurrent changes.
6. **Handle divergence.** If a push is non-fast-forward, inspect both sides; do not retry in a loop or force push automatically. If the worktree is clean and a fast-forward is possible, use pull --ff-only. When updating a task branch's base, merge according to repository conventions or rebase only this task's unpublished commits, then reverify. Preserve published history by default; explain the exact scope before rewriting history when the repository requires it. Resolve task conflicts autonomously when the goal and code make the intended result clear. Ask only when another person's change intent is material. Do not use an all-at-once ours or theirs override to bypass review.
7. **Verify outcomes.** After committing, confirm commit contents and remaining changes. After pushing, confirm the destination branch actually contains the task commit. Compare full SHAs only when exact identity matters for validation, delivery, or concurrency risk. Reuse evidence within the same boundary; recheck only when code or target state changes. Do not treat a command being sent or local success as proof of remote delivery.

## Standard pull request and issue workflow

- Before creating an issue or PR, query related open and closed items in the target repository. Confirm identifier, status, head/base, and task scope. Avoid duplicates. Do not automatically reopen a closed or merged item. If a request times out or its result is unclear, check whether it took effect before retrying.
- Choose a PR base based on repository contribution rules and the task goal; do not assume main. Inspect the complete base...head diff and commit list before creating a PR, and exclude unrelated commits. Do not casually change the base of an existing PR. Set the PR to draft or ready based on actual completeness, and preserve a maintainer's explicit requested state.
- Give the PR a specific title and follow the repository template. Describe the problem, final behavior, actual verification, and material limitations. **Ready for review:** mark the PR ready when implementation is complete and every required check that can run before readiness has passed. Keep it draft if implementation is incomplete, any such check failed or lacks passing evidence, or a draft was explicitly requested. Once ready, check the CI and reviews that require this state. Update stale PR text after code changes.
- In issues, distinguish confirmed facts, reproduction steps, expected and actual behavior, and unverified hypotheses. Do not invent environments, logs, or root causes. Use Fixes #... only when the issue is related and should close when this PR merges; otherwise use Refs #... to avoid accidental closure.
- Respond autonomously to specific review feedback on the current task, with reproduction and verification evidence. Confirm a required reply was successfully posted before resolving its discussion. Request review or use existing labels according to repository conventions. Prefer updating the existing description over adding noisy comments. Do not approve your own PR, assign people without reason, or close or reopen unrelated items. Close a related issue only after the fix is actually delivered and repository conventions support closure; prefer automatic closure on merge.
- After pushing, check CI and review results for the current head. Fix task-related failures, verify, and push follow-up changes until they pass or a clear external blocker remains. Do not delete tests, weaken assertions, or disable checks to get a green result. When waiting, report the current state; pending is not passing.
- **Automatic merge or queue:** when merging is in scope, the repository allows it, and the current head satisfies all requirements outside the platform's enforcement, use auto-merge or the queue only if the platform enforces every pending requirement. Check the head and base before enrolling and reassess if either changes. Report enrollment separately from a completed merge.
- **Direct merge:** reread the latest head SHA, base, mergeability, required CI, and review results. Merge when all required gates cover the current head and have passed. Assess whether base changes affect the evidence and use head-SHA matching when supported. Treat a watcher's READY verdict as a signal to check the actual gates. After either merge path, confirm the merged status and merge commit.
- For dependent PRs, merge in dependency order only when each PR's prerequisites and required gates are satisfied. A passing dependent PR does not permit skipping an unresolved prerequisite. After a prerequisite PR lands, reassess affected evidence and the remaining stack's actual state.
- Use CLI, MCP, API, or browser for authorized GitHub, Linear, and Notion operations, choosing an available capability. For ordinary tool failures, an equivalent channel may be used. Follow `SYSTEM.md` and the user's current task scope for authorization. Actual authentication failures, platform permissions or protections, and explicit execution-layer denials must be recorded and reported. These instructions do not provide credentials or override actual restrictions; do not use another channel to bypass a still-active execution-layer denial.
- In the final report, provide task branch, commit SHA, PR/issue link, and actual state as applicable. Distinguish committed, pushed, CI, merged, and blocked. Do not report “PR created” as “merged.”

## Commit message requirements

- End every commit message with a `Signed-off-by: <name> <email>` trailer using the repository's effective Git identity (`git config user.name` and `git config user.email`). Never hardcode a name or address. Before publishing, verify that the author, committer, and sign-off identities are intended for public use, and prefer a user-configured public or no-reply address where sign-off rules permit it. If the required identity is unset, report it and stop rather than inventing one.
